# 预算扫描：加大 max_tokens 能不能救回截断？——结论：不能

## 1. 四格补齐（G1j-2.9B-Q4，全部官方 demo 采样，各 200 题）

| 预算 | 思考 | 总分 | 截断 | 耗时 |
|---|---|---|---|---|
| 500 | 关（官方口径） | **44.2** | 90/200 = 45.0% | 14m |
| 8192 | 关 | **43.4** | **74/200 = 37.0%** | 117m |
| 8192 | 开 | 48.3 | 113/200 = 56.5% | 214m |
| 500 | 开 | 37.9 | 177/200 = 88.5% | 19m |

## 2. 预算扫描（在「关思考」下改判截断阈值，同一批生成结果）

| max_tokens | 截断 |
|--:|--:|
| 500 | 42.5% |
| 1024 | 39.0% |
| 2048 | 38.0% |
| 4096 | 38.0% |
| 8192 | 37.0% |

→ **1024 之后基本饱和**。预算翻 16 倍（500→8192），截断只从 45.0% 降到 37.0%。

## 3. 为什么：token 分布是强双峰

用 8192/关思考 的实际生成长度统计：

| 区间 | 题数 |
|---|--:|
| < 500 | **115**（58%） |
| 500–1k | 7 |
| 1k–2k | 2 |
| 2k–4k | 0 |
| 4k–8k | 2 |
| **= 8192** | **74**（37%） |

中间几乎是空的。说明题目分成两类：
* **多数题（58%）** 在 500 token 内自然收尾（中位数仅 395 token）；
* **约 37% 的题模型根本不吐 EOS**，不管给多少预算都会跑到上限。

→ **截断不是「预算不够」，是「约 74 道题模型不收尾」**。加大预算只是让这些题跑得更久更慢，
不解决终止问题；反而因为最后一轮跑偏，答案被稀释。

## 4. 加大预算的副作用：分数略降

500/关(44.2) → 8192/关(43.4)，**降 0.8**。逐题：**变大 36 / 变小 39 / 相同 125**。

典型「预算变大反而掉分」的题：

| 题 | 类别 | 分数变化 | token 变化 |
|---|---|---|---|
| Q12 | coding | 1.00 → 0.00 | 323 → 8192 |
| Q120 | coding | 1.00 → 0.00 | 500 → 8192 |
| Q137 | ruozhiba | 1.00 → 0.00 | 92 → 8192 |
| Q145 | longctx | 0.50 → 0.00 | 500 → 8192 |
| Q140 | ruozhiba | 1.00 → 0.00 | 500 → 0 |

`ruozhiba` 掉得最明显（85.0 → 50.0）：给足预算后模型在正确答案之后继续瞎聊，
而 harness 取**最后一条**「最终答案：」行，于是被后面的错误结论覆盖。

## 5. 结论与建议

1. **不要靠加大预算解决截断** —— 饱和点在 ~1024，之后 16 倍预算只换来 8 个百分点的改善。
2. **真正要修的是「不吐 EOS」这 37%**。两个方向：
   * 采样侧：官方 demo 的 `occurrence` 机制只在**生成期**累积、且随 0.99 衰减，
     长生成时罚项会衰减到接近 0（我的补丁复刻了同一语义）→ 长文段失去抑制，可能是根因；
   * 停止侧：harness 侧加「重复检测/最大连续无语义段」兜底，或对 coding/math 类题目
     检测到代码块/答案行即提前停。
3. **报数口径建议**：用 **500/关思考 = 44.2**（官方默认，最快 14m）；
   若要「答完率」，应同时报告截断率 45%，而不是偷偷把预算调到 8192 把分数做上去。
4. 注意 **8192/关思考(43.4) < 500/关思考(44.2)** —— 这条反直觉，说明该模型的
   benchmark 分数对预算并非单调，任何调预算的对比都必须同预算比。
